Every error raised by the SDK extends a common base class - `SandboxError` in TypeScript, `SandboxError` in Python - so you can catch it broadly or narrow down to a specific case.

## Error hierarchy

| TypeScript | Python | HTTP status | Meaning |
|---|---|---|---|
| `SandboxError` | `SandboxError` | - | Base class for every SDK error. |
| `AuthenticationError` | `AuthenticationError` | `401` | Missing or invalid API key / access token. |
| `ValidationError` | `ValidationError` | `400` | Request body or parameters rejected by the API. |
| `NotFoundError` | `NotFoundError` | `404` | Sandbox or resource does not exist. |
| `ConflictError` | `ConflictError` | `409` | Sandbox is not in a valid state for the operation (e.g., pausing an already-paused sandbox, or patching `network` rules while paused). |
| `BillingError` | `BillingError` | `402` | The team's billing or plan does not allow the sandbox to start. Branch on `code` and show `actionUrl` / `action_url` (see [Billing errors](#billing-errors-402)). |
| `RateLimitError` | `RateLimitError` | `429` | Rate limit or per-team quota reached. Branch on `code` (see below). |
| `TimeoutError` | `SandboxTimeoutError` | - | The SDK stopped waiting for a response. A command that reaches its own timeout doesn't throw: it returns exit code `124`. |
| `ServerError` | `ServerError` | `5xx` | Platform error - usually transient (500/502/503/504). GET/DELETE requests auto-retry with exponential backoff. |

<Note>
Python renames `TimeoutError` to `SandboxTimeoutError` so it doesn't shadow Python's built-in `TimeoutError`.
</Note>

## Catching a specific error

Catch the typed subclass you care about and fall back to `SandboxError` for everything else.

<CodeGroup>
```typescript TypeScript
import { NotFoundError, Sandbox, SandboxError } from "@superserve/sdk"

try {
  const sandbox = await Sandbox.connect("00000000-0000-0000-0000-000000000000")
} catch (err) {
  if (err instanceof NotFoundError) {
    // Sandbox doesn't exist or was already deleted
  } else if (err instanceof SandboxError) {
    // Any other SDK error
  }
}
```

```python Python
from superserve import NotFoundError, Sandbox, SandboxError

try:
    sandbox = Sandbox.connect("00000000-0000-0000-0000-000000000000")
except NotFoundError:
    # Sandbox doesn't exist or was already deleted
    pass
except SandboxError:
    # Any other SDK error
    pass
```
</CodeGroup>

## Base error properties

Every SDK error extends `SandboxError` and exposes:

- `statusCode?: number` / `status_code: int | None` - HTTP status, if the error originated from an API response
- `code?: string` / `code: str | None` - API-provided error code, when present

<CodeGroup>
```typescript TypeScript
import { Sandbox, SandboxError } from "@superserve/sdk"

try {
  await Sandbox.connect("00000000-0000-0000-0000-000000000000")
} catch (err) {
  if (err instanceof SandboxError) {
    console.error(err.statusCode, err.code, err.message)
  }
}
```

```python Python
from superserve import Sandbox, SandboxError

try:
    Sandbox.connect("00000000-0000-0000-0000-000000000000")
except SandboxError as err:
    print(err.status_code, err.code, err)
```
</CodeGroup>

## Idempotent operations

`kill()` / `kill_by_id()` swallow `404` internally - it's safe to call on a sandbox that was already deleted by another process. Every other method surfaces `NotFoundError` to the caller.

## Retries

The SDK automatically retries transient failures on `GET` and `DELETE` requests with exponential backoff and jitter:

- `429 Too Many Requests`
- `5xx` server errors
- Network errors (connection reset, DNS failure)

`POST` / `PATCH` requests are **not** retried automatically because they aren't safely idempotent - the SDK surfaces the error so you can decide.

## `RateLimitError`

Raised on `429` responses. Branch on `code` to distinguish the variant:

| Code | Endpoint(s) | Meaning |
|---|---|---|
| `rate_limited` | any | Request rate exceeded; retry after a short backoff. |
| `too_many_builds` | `POST /templates` | Team has reached its concurrent build limit. Wait for an active build to finish. |
| `too_many_templates` | `POST /templates` | Team has reached its total template count limit. Delete one or contact support. |
| `too_many_sandboxes` | `POST /sandboxes` | Team has reached its active sandbox count limit. Pause/delete one or contact support. |

The error `message` already includes the cap and a contact-support hint, so surfacing it directly to users is usually fine.

## Billing errors (`402`)

Creating or resuming a sandbox fails with `402 Payment Required` when the team's billing or plan does not allow it. This includes the automatic resume when you connect to a paused sandbox. The SDK raises `BillingError`, a subclass of `SandboxError`, with `statusCode` / `status_code` set to `402`. Branch on `code`:

| Code | Meaning | What to do |
|---|---|---|
| `trial_exhausted` | The team has no plan, and its free trial credit is used up or has expired. | Add a card and choose a plan at `action_url`, then retry. |
| `trial_unavailable` | The team has no plan and did not get the free trial, for example because it is not the first team its creator made. | Add a card and choose a plan at `action_url`, then retry. |
| `trial_check_unavailable` | The team has no plan, and the free trial could not be confirmed because a required check did not complete. This is not a decision that the team is ineligible. | Right after sign-up, wait a few seconds and retry once, because account setup can still be in progress. Otherwise, or if the code stays, add a card and choose a plan at `action_url`, or contact support@superserve.ai. Do not retry in a loop. |
| `billing_ineligible` | Sandbox usage is unavailable until billing is active, for a reason other than the trial codes above. An unpaid invoice is one example (see [Unpaid invoices](#unpaid-invoices)). The message is `Sandbox usage is unavailable until billing is active`. | Check the team's billing on the [Billing & Usage](https://console.superserve.ai/billing-usage) page: add a payment method, choose a plan, or pay the open invoice. Then retry. |
| `free_allowance_exhausted` | The team is on a legacy Free plan and has used its daily compute allowance. Running sandboxes are paused too. New accounts start on the free trial instead. | Wait until the allowance resets, or upgrade on the [Billing & Usage](https://console.superserve.ai/billing-usage) page for unlimited runtime. |
| `sandbox_exceeds_plan_limits` | The sandbox's vCPU, memory, or disk is larger than the team's plan allows. The message gives the sandbox size and the plan's limits. | Use a smaller template, or upgrade on the [Billing & Usage](https://console.superserve.ai/billing-usage) page. |

A team whose free trial was refused by an abuse or account check, for example because the creator's email domain is restricted, gets `billing_ineligible`, not `trial_unavailable`.

Some codes add a field to the `error` object of the API response. `BillingError` exposes `action_url` as `actionUrl` / `action_url` (`undefined` / `None` for other codes). The other fields stay in the raw API response, so read them from there if you need them:

- `action_url` (`trial_exhausted`, `trial_unavailable`, `trial_check_unavailable`): the console page where the team adds a card and chooses a plan. The `message` ends with the same URL, so a user who sees the message also gets the link.
- `resets_at` (`free_allowance_exhausted`): the UTC time (RFC 3339) when sandboxes can start again.
- `limits` (`sandbox_exceeds_plan_limits`): the plan's vCPU, memory, and disk maximums.

The error `message` is safe to show to users. The SDK never retries a `402`.

The CLI prints `action_url` in `--json` errors and waits for account setup after a browser sign-up (see [Scripting](/cli#scripting)). The MCP server tells the agent not to retry a trial or billing block (see [MCP troubleshooting](/integrations/mcp#troubleshooting)).

A billing block does not delete sandboxes on its own. A sandbox set to auto-delete after a pause can still be deleted while billing is blocked.

<CodeGroup>
```typescript TypeScript
import { BillingError, Sandbox } from "@superserve/sdk"

try {
  const sandbox = await Sandbox.create({ name: "billing-check" })
} catch (err) {
  if (err instanceof BillingError) {
    // Show the message, and the link when there is one
    console.error(err.code, err.message)
    if (err.actionUrl) console.error(`Add a card and choose a plan: ${err.actionUrl}`)
  } else {
    throw err
  }
}
```

```python Python
from superserve import BillingError, Sandbox

try:
    sandbox = Sandbox.create(name="billing-check")
except BillingError as err:
    # Show the message, and the link when there is one
    print(err.code, err)
    if err.action_url:
        print(f"Add a card and choose a plan: {err.action_url}")
```
</CodeGroup>

<Note>
`BillingError` is available in SDK 0.12.0 and later (`@superserve/sdk` and `superserve`). In earlier versions, a `402` raises the base `SandboxError` with the same `statusCode` / `status_code` and `code`, but without `actionUrl` / `action_url`. To support both, check `statusCode === 402` / `status_code == 402` on `SandboxError`. The CLI and MCP behavior above needs CLI 2.2.0 or later and MCP 0.4.0 or later.
</Note>

### Unpaid invoices

An unpaid invoice also returns `billing_ineligible`, on every plan. There is no separate code. When a card payment for an invoice is declined:

1. Billing members get one email for that invoice. It has links to pay the invoice and to update the payment method. It shows when sandboxes will be paused, or that they are paused already.
2. A temporary decline, such as insufficient funds, is retried once, 8 hours after the declined attempt. The email shows the retry time. A permanent decline, such as an expired, lost, or fraudulent card, is not retried. A payment that needs card authentication is not retried either.
3. If the invoice is still unpaid 24 hours after the first payment attempt, running sandboxes are paused, and new creates and resumes fail with `billing_ineligible`.

Superserve sometimes holds an invoice for review instead of charging it automatically. Superserve does not charge a held invoice, so a declined payment on it is not retried, and its email does not show a retry. If Superserve did not make the declined attempt itself, there is no 24-hour wait: sandboxes are paused as soon as Superserve records the decline, and the email says that they are paused.

Pay the invoice from the link in the email. Sandboxes can start again once the invoice is paid.

## `BuildError`

Raised by `Template.waitUntilReady()` / `wait_until_ready()` when the awaited build lands on status `failed`.

**Fields:**
- `code` - stable error prefix (`image_pull_failed`, `unsupported_base`, `step_failed`, `boot_failed`, `snapshot_failed`, `start_cmd_failed`, `ready_cmd_failed`, `capacity_unavailable`, `build_timed_out`, `infrastructure_failed`, `build_failed`)
- `buildId` / `build_id` - the build that failed
- `templateId` / `template_id` - the template id
- `message` - human-readable detail. The backend's `error_message` follows a `"<code>: <detail>"` convention (e.g. `"image_too_large: image is too large for the requested disk_mib"`); the SDK splits it so `code` holds the prefix and `message` holds the detail. When the backend doesn't include a prefix or message, `message` falls back to `"Template build failed"`.

See [BuildSpec reference: build error codes](/templates/build-spec#build-error-codes) for a full list of codes and their meanings.
