Because Superserve attaches credentials to outbound requests, every use of a secret is recorded. You get a full trail of what was sent where, with what result — without any cooperation from the code, and without trusting the sandbox.

## Requests made with a secret

`getAudit()` returns the requests authenticated with a secret, across every sandbox that used it, newest first:

<CodeGroup>
```typescript TypeScript
const secret = await Secret.get("anthropic-prod")
const events = await secret.getAudit({ limit: 50 })

for (const e of events) {
  console.log(e.ts, e.method, e.host + e.path, "→", e.status)
}
```

```python Python
secret = Secret.get("anthropic-prod")
events = secret.get_audit(limit=50)

for e in events:
    print(e.ts, e.method, f"{e.host}{e.path}", "→", e.status)
```
</CodeGroup>

Each event carries the sandbox that made it, the request line, and both the status returned to the sandbox and the `upstreamStatus` from the real service:

| Field | Description |
|---|---|
| `id` | Event ID. Pass it as `before` to page back |
| `ts` | When the request was made |
| `sandboxId` / `sandboxName` | The sandbox that used the secret (`sandboxName` is null if it's since been deleted) |
| `secretId` | The secret that was attached |
| `method` · `host` · `path` | The request line |
| `status` | Status returned to the sandbox |
| `upstreamStatus` | Status from the upstream service. Absent when the proxy answered the request itself |
| `latencyMs` | Round-trip time, in milliseconds |
| `errorCode` | Set when the proxy refused or failed the request, for example `credential_revoked` |

Python uses the snake_case names (`sandbox_id`, `upstream_status`, and so on).

A WebSocket connection is one event with `status` `101`, written when the connection opens. Messages sent over the open connection are not logged.

### Filtering

Narrow to a status class, or page back with the `before` cursor:

<CodeGroup>
```typescript TypeScript
// Only client/server errors.
const errors = await secret.getAudit({ status: "4xx" })

// Page back.
const older = await secret.getAudit({ before: errors.at(-1)!.id })
```

```python Python
errors = secret.get_audit(status="4xx")

older = secret.get_audit(before=errors[-1].id)
```
</CodeGroup>

| Option | Description |
|---|---|
| `limit` | Events per page. Default `100`, maximum `1000` |
| `before` | An event `id`. Returns only events older than it |
| `status` | `"2xx"`, `"3xx"`, `"4xx"`, `"5xx"`, or `"errors"` |

`"errors"` matches every request with a status of `400` or higher. This includes `4xx` and `5xx` responses from the upstream service, for example a `401` from a provider that rejected the credential. To find the requests the proxy refused or failed itself, keep the events that have an `errorCode`. Those events have no `upstreamStatus`.

The audit log keeps the last **7 days**. Older rows are dropped on a rolling basis; page the API if you want to keep a longer trail elsewhere.

## Sandboxes using a secret

To see where a secret is bound, `getSandboxes()` lists the live bindings:

<CodeGroup>
```typescript TypeScript
const bindings = await secret.getSandboxes()
for (const b of bindings) {
  console.log(b.sandboxName, "·", b.envKey, "·", b.status)
}
```

```python Python
for b in secret.get_sandboxes():
    print(b.sandbox_name, "·", b.env_key, "·", b.status)
```
</CodeGroup>

The audit log records only requests that carried a secret. A request the proxy refused before it attached a secret, for example a request to a host your network rules don't allow, is not in the audit log. Look for it in the sandbox's [network log](/sandbox/network-log).

<Tip>
For the full picture of a single sandbox's traffic — not just secret-bearing requests, but every HTTP and HTTPS connection it made to a public address on ports 80 and 443 — use the [network log](/sandbox/network-log).
</Tip>
