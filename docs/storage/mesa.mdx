[Mesa](https://mesa.dev/) is a versioned virtual filesystem you can mount inside a Superserve sandbox. Where a [cloud bucket](/storage/cloud-buckets) gives a sandbox flat object storage, Mesa adds version history and branches, so every edit is committed back and each sandbox can fork its own workspace. This guide covers the full flow: use the Mesa SDK outside the sandbox to set up resources, then the Superserve SDK to mount Mesa inside.

Mounting Mesa in a Superserve sandbox takes three steps:

1. **Outside the sandbox:** use the Mesa SDK (TypeScript or Python) to create repos, describe the mount as a [layout](https://docs.mesa.dev/content/mesafs/layouts), mint a short-lived access token for it, and orchestrate your workflow.
2. **Inside the sandbox:** install the `mesa` CLI, write the layout file, and run `mesa mount --layout layout.json --daemonize` with the access token to mount your repos as local directories.
3. **Run your agent:** `cd` into the mount path and launch your agent (e.g. Claude Code, Codex, or a custom agent). Any file edits are automatically persisted back to Mesa.

For details on FUSE setup, system dependencies, and container configuration, see Mesa's [POSIX Mount guide](https://docs.mesa.dev/content/mesafs/posix-mount).

## Sandbox setup

Superserve sandboxes run on a FUSE-enabled kernel, and the Mesa installer apt-installs `fuse3` as a dependency. Because Superserve sandboxes are full Firecracker microVMs, you don't need `user_allow_other` or `chmod 666 /dev/fuse`.

The Mesa installer needs root. `superserve/base` and `superserve/claude-code` run commands as `root`, so the install works as is. On a template with a non-root default user, such as `superserve/desktop`, pass `user: "root"` to the install command.

The example below uses `superserve/claude-code`, which ships the Claude Code CLI, and binds your Anthropic key as a [secret](/secrets/overview) named `anthropic-key`. On other templates, install your agent before you run it.

<CodeGroup>
```typescript TypeScript
import { Sandbox } from "@superserve/sdk";
import { Mesa, repo } from "@mesadev/sdk";

const mesa = new Mesa({ privateKey: process.env.MESA_PRIVATE_KEY });

// --- Outside the sandbox: set up Mesa resources ---

// Create a repo (or use an existing one)
await mesa.repos.create({ name: "agent-workspace" });

// Mount the repo at /workspace and mint a scoped, self-expiring access token
// for that layout. Signed locally from your private key, so the key never
// enters the sandbox.
const workspace = mesa.fs({
  layout: { "/workspace": repo("agent-workspace", { mode: "rw" }) },
  authors: [{ name: "Agent", email: "agent@example.com" }],
  ttl: 3600, // 1 hour
});
const { token } = await workspace.token();

// --- Inside the sandbox: install and mount Mesa ---

const sandbox = await Sandbox.create({
  name: "mesa-agent",
  fromTemplate: "superserve/claude-code",
  secrets: { ANTHROPIC_API_KEY: "anthropic-key" },
});

// Install the Mesa CLI. The installer apt-installs fuse3 as a dependency.
await sandbox.commands.run(
  "curl -fsSL https://mesa.dev/install.sh | sh -s -- --version latest --yes",
);

// Write the layout file, then start Mesa as a background daemon.
// MESA_ACCESS_TOKEN is read from the environment, never persisted to disk.
await sandbox.files.write(
  "/home/user/layout.json",
  JSON.stringify(workspace.layout()),
);
await sandbox.commands.run("mesa mount --layout /home/user/layout.json --daemonize", {
  env: { MESA_ACCESS_TOKEN: token },
});

// --- Run your agent ---

await sandbox.commands.run(
  'cd ~/.local/share/mesa/mnt/workspace && claude -p --permission-mode acceptEdits "Implement the feature described in TODO.md"',
);
```

```python Python
import asyncio
import json
import os

from mesa_sdk import Mesa, repo
from superserve import Sandbox


async def main():
    # --- Outside the sandbox: set up Mesa resources (the Mesa SDK is async) ---
    async with Mesa(private_key=os.environ["MESA_PRIVATE_KEY"]) as mesa:
        # Create a repo (or use an existing one)
        await mesa.repos.create(name="agent-workspace")

        # Mount the repo at /workspace and mint a scoped, self-expiring access token
        # for that layout. Signed locally from your private key, so the key never
        # enters the sandbox.
        workspace = mesa.fs(
            layout={"/workspace": repo("agent-workspace", mode="rw")},
            authors=[{"name": "Agent", "email": "agent@example.com"}],
            ttl=3600,  # 1 hour
        )
        minted = await workspace.token()

    # --- Inside the sandbox: install and mount Mesa ---
    sandbox = Sandbox.create(
        name="mesa-agent",
        from_template="superserve/claude-code",
        secrets={"ANTHROPIC_API_KEY": "anthropic-key"},
    )

    # Install the Mesa CLI. The installer apt-installs fuse3 as a dependency.
    sandbox.commands.run(
        "curl -fsSL https://mesa.dev/install.sh | sh -s -- --version latest --yes"
    )

    # Write the layout file, then start Mesa as a background daemon.
    # MESA_ACCESS_TOKEN is read from the environment, never persisted to disk.
    sandbox.files.write("/home/user/layout.json", json.dumps(workspace.layout()))
    sandbox.commands.run(
        "mesa mount --layout /home/user/layout.json --daemonize",
        env={"MESA_ACCESS_TOKEN": minted.token},
    )

    # --- Run your agent ---
    sandbox.commands.run(
        "cd ~/.local/share/mesa/mnt/workspace "
        '&& claude -p --permission-mode acceptEdits "Implement the feature described in TODO.md"'
    )


asyncio.run(main())
```

```bash CLI
# Install the Mesa CLI. The installer apt-installs fuse3 as a dependency.
curl -fsSL https://mesa.dev/install.sh | sh -s -- --version latest --yes

# Start Mesa as a background daemon. layout.json is the serialized layout, and
# MESA_ACCESS_TOKEN is the token minted for it, read from the environment.
MESA_ACCESS_TOKEN="$MESA_TOKEN" mesa mount --layout layout.json --daemonize

# Run your agent
cd ~/.local/share/mesa/mnt/workspace
claude -p --permission-mode acceptEdits "Implement the feature described in TODO.md"
```

## Custom template

For faster startup, pre-install the Mesa CLI into a [custom Superserve template](/templates/create) so each sandbox boots with the Mesa CLI already installed:

<CodeGroup>
```typescript TypeScript
import { Template } from "@superserve/sdk";

const template = await Template.create({
  name: "agent-with-mesa",
  vcpu: 2,
  memoryMib: 2048,
  diskMib: 4096,
  from: "ubuntu:24.04",
  steps: [
    {
      run: "apt-get update && apt-get install -y --no-install-recommends ca-certificates curl git && rm -rf /var/lib/apt/lists/*",
    },
    { run: "curl -fsSL https://mesa.dev/install.sh | sh -s -- --version latest --yes" },
  ],
});

await template.waitUntilReady();
```

```python Python
from superserve import Template, RunStep

template = Template.create(
    name="agent-with-mesa",
    vcpu=2,
    memory_mib=2048,
    disk_mib=4096,
    from_="ubuntu:24.04",
    steps=[
        RunStep(
            run="apt-get update && apt-get install -y --no-install-recommends ca-certificates curl git && rm -rf /var/lib/apt/lists/*"
        ),
        RunStep(run="curl -fsSL https://mesa.dev/install.sh | sh -s -- --version latest --yes"),
    ],
)

template.wait_until_ready()
```

```dockerfile Dockerfile
FROM ubuntu:24.04
RUN apt-get update && apt-get install -y --no-install-recommends ca-certificates curl git \
    && rm -rf /var/lib/apt/lists/*
RUN curl -fsSL https://mesa.dev/install.sh | sh -s -- --version latest --yes
```
</CodeGroup>

## Tips

- **Use scoped, short-lived access tokens.** Mint a dedicated token for each sandbox session from a layout that declares only the repos it needs. It's signed locally from your private key (which never enters the sandbox) and expires on its own. See Mesa's [Authentication](https://docs.mesa.dev/content/concepts/authentication) docs for details.
- **Use `--daemonize`.** Always run `mesa mount --daemonize` in sandbox environments so Mesa runs as a background process and doesn't block your agent's terminal.
- **Build a custom template** for production use. Pre-installing the Mesa CLI avoids the install overhead on every sandbox creation.
- **Mount path follows `$HOME`.** Each layout path appears under `~/.local/share/mesa/mnt/` for the user that runs `mesa mount`, so `/workspace` lands at `~/.local/share/mesa/mnt/workspace`. On `superserve/base` and `superserve/claude-code`, `HOME` is `/home/user`. On `superserve/desktop` the default user's `HOME` is `/home/desktop`, so run the mount and your agent as the same user and use `~/` paths.
