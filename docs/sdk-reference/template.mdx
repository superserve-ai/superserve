The `Template` class creates and manages reusable sandbox base images. Templates are built once and then used to launch any number of identically configured sandboxes in seconds.

See the [Templates overview](/templates/overview) for concepts, or jump to the [Create a template](/templates/create) guide for the end-to-end flow.

## Import

<CodeGroup>
```typescript TypeScript
import { Template } from "@superserve/sdk"
```

```python Python
from superserve import Template
# Step types for the `steps` array:
from superserve import RunStep, EnvStep, EnvStepValue, WorkdirStep, UserStep, UserStepValue
# Async variant (await every method):
from superserve import AsyncTemplate
```
</CodeGroup>

Python ships both a sync `Template` and an `AsyncTemplate` with the same methods. See [Async (Python)](#async-python).

## Factory methods

### `Template.create`

Register a new template and queue its first build. Returns as soon as the template row exists and a `build_id` is assigned - the build itself runs asynchronously. Call [`waitUntilReady`](#waituntilready-/-wait_until_ready) to block until the build finishes.

<CodeGroup>
```typescript TypeScript
const template = await Template.create({
  name: "my-python-env",
  vcpu: 2,
  memoryMib: 2048,
  diskMib: 4096,
  from: "python:3.11",
  steps: [
    { run: "pip install numpy pandas" },
    { env: { key: "DEBUG", value: "1" } },
    { workdir: "/app" },
    { user: { name: "appuser", sudo: true } },
  ],
  startCmd: "python -m http.server 8080",
  readyCmd: "curl -f http://localhost:8080/",
})
```

```python Python
from superserve import Template, RunStep, EnvStep, EnvStepValue, WorkdirStep, UserStep, UserStepValue

template = Template.create(
    name="my-python-env",
    vcpu=2,
    memory_mib=2048,
    disk_mib=4096,
    from_="python:3.11",
    steps=[
        RunStep(run="pip install numpy pandas"),
        EnvStep(env=EnvStepValue(key="DEBUG", value="1")),
        WorkdirStep(workdir="/app"),
        UserStep(user=UserStepValue(name="appuser", sudo=True)),
    ],
    start_cmd="python -m http.server 8080",
    ready_cmd="curl -f http://localhost:8080/",
)
```
</CodeGroup>

**Options:**

| Option | Type | Description |
|---|---|---|
| `name` | `string` | **Required.** Team-scoped identifier. Must not start with `superserve/`. Names are unique per team among non-deleted templates and are released for reuse the moment a template is deleted. |
| `from` / `from_` | `string` | **Required.** OCI base image (e.g. `python:3.11`). See [BuildSpec](/templates/build-spec#from-base-image). |
| `vcpu` | `number` | Number of vCPUs. Minimum 1 vCPU. Maximum 2 vCPU on Free, 4 vCPU on Developer, 16 vCPU on Pro. Default `1` (1 vCPU). See [Resource limits](/templates/build-spec#resource-limits). |
| `memoryMib` / `memory_mib` | `number` | Memory in MiB. Minimum 256 MiB. Maximum 4096 MiB (4 GiB) on Free, 16384 MiB (16 GiB) on Developer, 65536 MiB (64 GiB) on Pro. Default `1024` (1 GiB). |
| `memoryMaxMib` / `memory_max_mib` | `number` | Optional ceiling sandboxes can grow memory to while running; `memoryMib` stays the boot size. Must be greater than `memoryMib`, at most 4 times it and within your plan's memory limit, and differ from it by a multiple of 128. Omit for a fixed memory size. See [Growing memory](/templates/build-spec#growing-memory). |
| `diskMib` / `disk_mib` | `number` | Disk in MiB. Minimum 1024 MiB (1 GiB). The maximum depends on your team's plan. Default `4096` (4 GiB). |
| `steps` | [`BuildStep[]`](#buildstep) | Ordered build steps. |
| `startCmd` / `start_cmd` | `string` | Long-running process captured in the snapshot. |
| `readyCmd` / `ready_cmd` | `string` | Readiness probe polled every 2s after `startCmd`. |
| `apiKey` / `api_key` | `string` | Overrides `SUPERSERVE_API_KEY`. |
| `baseUrl` / `base_url` | `string` | Overrides `SUPERSERVE_BASE_URL`. |
| `signal` | `AbortSignal` | TypeScript only - abort the creation request. |

Throws `SandboxError` if the API response is missing `build_id`.

## Methods on `template`

### `getInfo` / `get_info`

Fetch the current server-side state. Returns a fresh [`TemplateInfo`](#templateinfo) - the `template`'s own properties are snapshots and are **not** mutated.

<CodeGroup>
```typescript TypeScript
const info = await template.getInfo()
console.log(info.status)  // "pending" | "building" | "ready" | "failed"
```

```python Python
info = template.get_info()
print(info.status.value)  # "pending" | "building" | "ready" | "failed"
```
</CodeGroup>

### `waitUntilReady` / `wait_until_ready`

Block until the template's current build reaches a terminal status. The build is `latestBuildId` / `latest_build_id` when the object has one (set by `Template.create`), otherwise the most recent build. After [`rebuild`](#rebuild), wait on the returned build ID instead. The SDK polls `GET /templates/{id}/builds/{buildId}` for the authoritative build status — SSE is used only for live log delivery when `onLog` / `on_log` is provided, never to detect termination. Returns a refreshed [`TemplateInfo`](#templateinfo) with `status = "ready"`.

<CodeGroup>
```typescript TypeScript
const info = await template.waitUntilReady({
  onLog: (event) => {
    if (event.stream === "system") return
    console.log(event.text)
  },
})
```

```python Python
def print_log(ev):
    if ev.stream.value != "system":
        print(ev.text)

info = template.wait_until_ready(on_log=print_log)
```
</CodeGroup>

**Options:**

| Option | Type | Description |
|---|---|---|
| `onLog` / `on_log` | `(ev: BuildLogEvent) => void` | Called for each log line while the build runs. Not called if the build already finished. |
| `signal` | `AbortSignal` | TypeScript only - aborts the stream and any pending poll. |
| `pollIntervalMs` | `number` | TypeScript only. Build status poll interval. Default `2000`. |
| `poll_interval_s` | `float` | Python only. Build status poll interval. Default `2.0`. |

**Throws:**

- `BuildError` if the build transitions to `failed`. The backend's `error_message` follows a `"<code>: <detail>"` convention; the SDK splits it so `BuildError.code` is the stable prefix and `BuildError.message` is the human-readable detail. See [BuildSpec: Build error codes](/templates/build-spec#build-error-codes).
- `ConflictError` if the build is `cancelled`

Logs stream only while the build runs. If the build already finished, `onLog` / `on_log` is never called, and the method returns or throws from the build's final status as usual. The SDK can't replay the logs of a finished build, so save the events in your callback if you need them later.

### `streamBuildLogs` / `stream_build_logs`

Pure SSE stream of build logs. Returns when the stream closes. Does **not** wait for a terminal status - use `waitUntilReady` for that.

<CodeGroup>
```typescript TypeScript
await template.streamBuildLogs({
  onEvent: (ev) => {
    console.log(`[${ev.stream}] ${ev.text}`)
  },
  // buildId defaults to template.latestBuildId, otherwise the most recent build
})
```

```python Python
from superserve import SandboxError

def on_event(ev):
    print(f"[{ev.stream.value}] {ev.text}")

try:
    # build_id defaults to template.latest_build_id, otherwise the most recent build
    template.stream_build_logs(on_event=on_event)
except SandboxError as err:
    # Raised when the stream ends; every log line was already delivered.
    if "missing timestamp" not in str(err):
        raise
```
</CodeGroup>

**Options:**

| Option | Type | Description |
|---|---|---|
| `onEvent` / `on_event` | `(ev: BuildLogEvent) => void` | **Required.** Called for every event. |
| `buildId` / `build_id` | `string` | Target build. Defaults to `latestBuildId` / `latest_build_id`, otherwise the most recent build. |
| `signal` | `AbortSignal` | TypeScript only - aborts the stream. |

Throws `SandboxError` if no `buildId` is supplied and the template has no builds.

The stream carries log lines only while the build runs. For a build that already finished, TypeScript returns without calling `onEvent`.

In Python, `stream_build_logs` raises `SandboxError("Invalid log event: missing timestamp")` when the stream ends, because the stream's final event has no timestamp. It raises after it delivered every log line, and for a finished build it raises without calling `on_event`. The example above ignores that error. `wait_until_ready(on_log=...)` doesn't raise it.

### `rebuild`

Queue a new build for this template. Returns the new [`TemplateBuildInfo`](#templatebuildinfo). Idempotent: if an in-flight build already matches the same configuration, the existing build is returned.

`rebuild()` does not update `latestBuildId` / `latest_build_id`. On a template returned by `Template.create`, `waitUntilReady()` / `wait_until_ready()` keeps waiting on the first build. To wait for the new build, poll the returned build ID with [`getBuild`](#getbuild-/-get_build):

<CodeGroup>
```typescript TypeScript
const build = await template.rebuild()

let current = build
while (!["ready", "failed", "cancelled"].includes(current.status)) {
  await new Promise((resolve) => setTimeout(resolve, 2000))
  current = await template.getBuild(build.id)
}
console.log(current.status, current.errorMessage ?? "")
```

```python Python
import time

build = template.rebuild()

while build.status.value not in ("ready", "failed", "cancelled"):
    time.sleep(2)
    build = template.get_build(build.id)
print(build.status.value, build.error_message or "")
```
</CodeGroup>

## Properties on `template`

All properties are read-only snapshots taken at construction. Call `getInfo()` / `get_info()` to refresh.

| Property | Type | Description |
|---|---|---|
| `id` | `string` | Template UUID. |
| `name` | `string` | Team-scoped identifier. |
| `teamId` / `team_id` | `string` | Owning team UUID. |
| `status` | `TemplateStatus` | Status at construction time. |
| `vcpu` | `number` | vCPU count the template boots with. |
| `memoryMib` / `memory_mib` | `number` | Memory the template boots with. |
| `memoryMaxMib?` / `memory_max_mib?` | `number` | Ceiling memory can grow to while running; absent when memory is fixed. |
| `diskMib` / `disk_mib` | `number` | Disk the template boots with. |
| `sizeBytes?` / `size_bytes?` | `number` | Snapshot size in bytes, once built. |
| `errorMessage?` / `error_message?` | `string` | Last build's error message, if any. |
| `createdAt` / `created_at` | `Date` / `datetime` | When the template row was created. |
| `builtAt?` / `built_at?` | `Date` / `datetime` | When the latest successful build finished. |
| `latestBuildId?` / `latest_build_id?` | `string` | Most recent build UUID. |

## Async (Python)

`AsyncTemplate` has the same methods and options as `Template`. Every method that calls the API is a coroutine, including `AsyncTemplate.create`, `connect`, `list`, and `delete_by_id`. The `on_log` and `on_event` callbacks stay regular functions; don't pass a coroutine function. `AsyncSandbox.create` takes an `AsyncTemplate` as `from_template`.

```python
import asyncio

from superserve import AsyncSandbox, AsyncTemplate, RunStep


async def main():
    template = await AsyncTemplate.create(
        name="my-async-env",
        from_="python:3.11",
        steps=[RunStep(run="pip install requests")],
    )
    try:
        await template.wait_until_ready(on_log=lambda ev: print(ev.text))
        builds = await template.list_builds()
        print(builds[0].status.value)  # "ready"

        sandbox = await AsyncSandbox.create(name="async-run", from_template=template)
        try:
            result = await sandbox.commands.run("python -c 'import requests; print(requests.__version__)'")
            print(result.stdout)
        finally:
            await sandbox.kill()
    finally:
        await template.delete()


asyncio.run(main())
```

## Types

### `TemplateStatus`

<CodeGroup>
```typescript TypeScript
type TemplateStatus = "pending" | "building" | "ready" | "failed"
```

```python Python
from enum import Enum

class TemplateStatus(str, Enum):
    PENDING = "pending"
    BUILDING = "building"
    READY = "ready"
    FAILED = "failed"
```
</CodeGroup>

- `pending` - template exists; first build is queued
- `building` - a build is in progress
- `ready` - at least one successful build exists; sandboxes can boot from this template
- `failed` - the latest build failed; rebuild or fix the spec

### `BuildLogEvent`

<CodeGroup>
```typescript TypeScript
interface BuildLogEvent {
  timestamp: Date
  stream: "stdout" | "stderr" | "system"
  text: string
  finished?: boolean
  status?: "ready" | "failed" | "cancelled"
}
```

```python Python
from datetime import datetime
from pydantic import BaseModel

class BuildLogEvent(BaseModel):
    timestamp: datetime
    stream: BuildLogStream        # "stdout" | "stderr" | "system"
    text: str
    finished: bool | None = None
    status: str | None = None     # "ready" | "failed" | "cancelled"
```
</CodeGroup>

`stream == "system"` events are status messages from the build runner (build-step boundaries, snapshot progress). Filter them out when rendering to a user-facing console. Each event's `text` holds one line, without a trailing newline.

The API ends each stream with a `finished: true` event that carries the terminal `status`. That event has no `timestamp`, so the SDKs don't pass it to your callback. Use `waitUntilReady` / `wait_until_ready` or `getBuild` / `get_build` for the build's final status.

### `BuildStep`

A discriminated union - exactly one of `run` / `env` / `workdir` / `user` must be set per step. See [BuildSpec: Steps](/templates/build-spec#steps-ordered-build-steps) for semantics.

<CodeGroup>
```typescript TypeScript
type BuildStep =
  | { run: string }
  | { env: { key: string; value: string } }
  | { workdir: string }
  | { user: { name: string; sudo?: boolean } }
```

```python Python
from pydantic import BaseModel

class RunStep(BaseModel):
    run: str

class EnvStepValue(BaseModel):
    key: str
    value: str

class EnvStep(BaseModel):
    env: EnvStepValue

class WorkdirStep(BaseModel):
    workdir: str

class UserStepValue(BaseModel):
    name: str
    sudo: bool = False

class UserStep(BaseModel):
    user: UserStepValue

BuildStep = RunStep | EnvStep | WorkdirStep | UserStep
```
</CodeGroup>

### `BuildError`

Thrown by `waitUntilReady` / `wait_until_ready` when the build transitions to `failed`.

<CodeGroup>
```typescript TypeScript
class BuildError extends SandboxError {
  readonly code: string        // e.g. "image_pull_failed" | "step_failed" | ...
  readonly message: string     // human-readable detail (prefix stripped)
  readonly buildId: string
  readonly templateId: string
}
```

```python Python
class BuildError(SandboxError):
    code: str             # e.g. "image_pull_failed" | "step_failed" | ...
    # `str(err)` returns the human-readable detail (prefix stripped)
    build_id: str
    template_id: str
```
</CodeGroup>

The backend's `error_message` follows a `"<code>: <detail>"` convention (e.g. `"image_too_large: image is too large for the requested disk_mib"`). The SDK splits it so `code` holds the prefix and the error message holds the detail. When the backend doesn't include a prefix, `code` falls back to `"build_failed"` and the message falls back to `"Template build failed"`.

See the [full list of build error codes](/templates/build-spec#build-error-codes) and the general [Errors](/errors) reference.

## Retries

GET and DELETE requests (including `Template.list`, `Template.connect`, `getInfo`, `listBuilds`, `getBuild`, `cancelBuild`, `delete`, `deleteById`) auto-retry on `429`, `502`, `503`, `504`, and network errors with exponential backoff + jitter (3 attempts max). POST requests (`create`, `rebuild`) are not retried - the SDK surfaces the error so you can decide.

## Errors

Template methods commonly raise:

- `AuthenticationError` - missing or invalid API key
- `ValidationError` - bad request body (invalid name, unsupported base image, steps with multiple keys)
- `NotFoundError` - template or build doesn't exist (except `delete` / `deleteById` / `cancelBuild`, which swallow 404)
- `ConflictError` - template has dependent sandboxes (on delete) or build was cancelled (on `waitUntilReady`)
- `BuildError` - build transitioned to `failed` (from `waitUntilReady` only)
- `ServerError` - platform error

See [Errors](/errors) for the full hierarchy.
